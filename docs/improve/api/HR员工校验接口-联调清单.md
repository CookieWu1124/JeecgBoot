# HR 员工校验接口 — 联调清单（提案小程序短信登录）

> **状态**：草案，待双方确认后冻结  
> **日期**：2026-09-05  
> **定稿依据**：[手机短信验证登录流程-简化版.md](../assets/sms-login/手机短信验证登录流程-简化版.md)  
> **调用方**：提案改善系统后端（JeecgBoot）  
> **提供方**：HR 系统  
> **用途**：发验证码前，用「工号 + 手机号」判断是否在职，并带回可落库档案字段  
> **说明**：小程序前端不直连 HR；**前端不传员工包、不传 openid**。

---

## 1. 调用时机（提案侧）

| 时机 | 是否调本接口 |
|------|----------------|
| 用户点击「获取验证码」 | **是**（唯一调用点；且须已通过绑定冲突检查） |
| 用户提交短信验证码登录 | **否**（用发码时 Redis 票据里的 HR 回传） |
| Token 空闲未超时 | **否** |
| Token 空闲超时后再次发码 | **是** |

HR 失败 / 非在职：提案侧提示「该账号不可用」或「发送失败，请稍后重试」，**不发短信**。

---

## 2. 接口约定（请 HR 实现）

### 2.1 基本信息

| 项 | 约定 |
|----|------|
| 方向 | 提案后端 → HR |
| 方法 | `POST` |
| Content-Type | `application/json; charset=UTF-8` |
| 路径 | **待 HR 提供**（示例：`/api/hr/employee/verifyForLogin`） |
| 鉴权 | **待双方约定**（内网 IP 白名单 / 固定 Token / mTLS 等） |
| 超时 | 提案侧建议 ≤ 3s；超时不发码，提示「发送失败，请稍后重试」并告警 |
| 幂等 | 同一工号+手机短时间重复调用结果应一致 |

### 2.2 请求体

```json
{
  "workNo": "600013",
  "mobile": "13800138000"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `workNo` | string | 是 | 员工工号；去除首尾空格 |
| `mobile` | string | 是 | 登录页填写的手机号；提案侧已按国内 11 位规范化（去空格、去 `+86`/`86`） |

### 2.3 响应体（统一包）

```json
{
  "success": true,
  "code": "0",
  "message": "ok",
  "data": { }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `success` | boolean | 是否在职可发码 |
| `code` | string | 见 §2.4 |
| `message` | string | 说明；提案可映射文案 |
| `data` | object \| null | 仅在职（`code=0`）时有值 |

### 2.4 业务码（按简化版：HR 只判是否在职）

简化版约定：**不要再拆**「工号是否存在 / 手机是否配套」给前端不同文案；非在职（含号不对、查无等）统一按不可用处理。

| code | success | 含义 | 提案侧提示 |
|------|---------|------|------------|
| `0` | true | **在职**（工号+手机在 HR 侧有效配套） | — |
| `1003` | false | **非在职**（离职、停用、工号/手机无效或不配套等） | 该账号不可用 |
| `1099` | false | 其它业务拒绝 | 该账号不可用（或透传 `message`） |

> 若 HR 内部仍区分「号不存在 / 手机不配 / 离职」，可在 `message` 里写明细供排障，但对外业务码建议收敛为上表，避免前端多种提示。  
> HTTP：业务拒绝用 **200 + code**；网络/鉴权/5xx 由提案映射为「发送失败，请稍后重试」。

## 3. 成功时 `data` 字段清单

在职时同一条结果带回档案字段；**缺的字段存空字符串，不挡发码**（简化版口径）。  
登录成功后写入本地；发码阶段整包进 Redis 票据（约 5 分钟）。

### 3.1 身份（建议有值）

| 字段 | 类型 | 说明 | 本地落点 |
|------|------|------|----------|
| `workNo` | string | 须与请求一致 | `username` = `work_no` |
| `realname` | string | 姓名 | `sys_user.realname` |
| `mobile` | string | 登记手机（建议与请求一致） | `sys_user.phone` |
| `employStatus` | string | 固定 `ACTIVE`（仅在职成功时出现） | `status=1` |

### 3.2 组织（建议有值；用于匹配本地部门树）

| 字段 | 类型 | 说明 | 本地落点 |
|------|------|------|----------|
| `centerName` | string | 中心，如「斯派科」 | 匹配 `sys_depart` CENTER |
| `deptName` | string | 部门 | 匹配 DEPT |
| `groupName` | string | 组别；无组别可 `""`，挂到部门节点 | 匹配 GROUP |

匹配规则：按名称路径对齐本地已导组织；**不要**把 HR 小组编码写入 Jeecg `org_code`。  
匹配失败时的提案行为：实现阶段定（可挡发码并提示组织未同步，或先发码登录成功再告警）——联调前与提案开发确认。当前建议：**对不上则不发码**，提示「组织未同步，请联系管理员」。

### 3.3 三级审批人（组织汇报链；缺则空串）

| 字段 | 类型 | 说明 |
|------|------|------|
| `approverL1WorkNo` / `approverL1Name` | string | 一级审批人工号 / 姓名 |
| `approverL2WorkNo` / `approverL2Name` | string | 二级 |
| `approverL3WorkNo` / `approverL3Name` | string | 三级 |

写入员工档案快照，**不自动覆盖**提案委员会 / 部门负责人 / 批准人配置。

### 3.4 选填

| 字段 | 说明 |
|------|------|
| `positionName` | 岗位名称；有则写入 `sys_user.position_type` |
| `hrGroupCode` | HR 小组编码，仅对账，不写 `org_code` |
| `jobLevelCode` / `jobLevelName` / `hireDate` | 职级、聘用日；暂可不落库 |

> **不要求**：`email`。

## 5. 提案侧落库边界（非 HR 实现项）

| 类别 | 行为 |
|------|------|
| 用户主数据 | 登录成功按 `workNo`：**无则创建，有则更新**（姓名、手机、组织挂载、岗位等） |
| 三级审批人 | 档案快照；不写 `proposal_*` 配置表 |
| 不覆盖 | `password` / `salt`、角色、提案配置名册 |
| 微信绑定 | `sys_third_account`；发码时用 `code` 换 openid，登录成功才写入 |
| 本系统尚无该工号 | **不挡发码**；登录成功时建档 |

新建用户：`username=workNo`；开发期仍可保留小程序密码通道测号，目标态以短信为准。

## 7. 与发码流程的关系（简化版顺序）

1. 发码入参：工号 + 手机 + 微信 `code`（登录不再带 `code`）  
   - **发码** = 发 6 位**短信**验证码；**换 openid** = 发码接口内用微信 `code` 换身份，二者勿混（见简化版文首术语表）  
2. 提案：格式 → IP 限额 → 换 openid → **绑定冲突检查** → **调本 HR 接口** → 手机冷却/日限 → 发短信  
3. HR `data` + openid + 验证码写入 Redis 票据 `wxmini:sms:ticket:{工号}:{手机}`（5 分钟）  
4. 登录成功：比对验证码 → 写绑定 → 按 HR 回传建档/更新 → 发 Token
