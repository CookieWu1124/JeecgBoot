# HR 员工校验接口 — 联调清单（提案小程序短信登录）

> **状态**：草案，待双方确认后冻结  
> **日期**：2026-09-05  
> **调用方**：提案改善系统后端（JeecgBoot）  
> **提供方**：HR 系统  
> **用途**：小程序「工号 + 登记手机 + 短信验证码」登录时，校验人号配套并拉取可落库档案字段  
> **说明**：本文只约定 **HR ↔ 提案后端** 接口；小程序前端不直连 HR。

---

## 1. 调用时机（提案侧）

| 时机 | 是否调本接口 |
|------|----------------|
| 用户点击「获取验证码」 | **是**（唯一调用点） |
| 用户提交短信验证码登录 | **否**（用发码时缓存的 HR 快照） |
| Token 仍有效进入工作台 | **否** |
| Token 失效后再次发码 | **是**（与首次相同） |

失败时提案后端直接返回前端错误文案，**不发短信**。

---

## 2. 接口约定（请 HR 实现）

### 2.1 基本信息

| 项 | 约定 |
|----|------|
| 方向 | 提案后端 → HR |
| 方法 | `POST` |
| Content-Type | `application/json; charset=UTF-8` |
| 路径 | **待 HR 提供**（示例：`/api/hr/employee/verifyForLogin`） |
| 鉴权 | **待双方约定**（内网 IP 白名单 / 固定 Token / mTLS 等） |
| 超时 | 提案侧建议 ≤ 3s；超时视为 HR 不可用 |
| 幂等 | 同一工号+手机短时间重复调用结果应一致 |

### 2.2 请求体

```json
{
  "workNo": "600013",
  "mobile": "13800138000"
}
```

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `workNo` | string | 是 | 员工工号；与提案登录账号一致，去除首尾空格 |
| `mobile` | string | 是 | 用户在登录页填写的手机号；11 位大陆号，提案侧会先做格式校验 |

### 2.3 响应体（统一包）

```json
{
  "success": true,
  "code": "0",
  "message": "ok",
  "data": { }
}
```

| 字段 | 类型 | 说明 |
|------|------|------|
| `success` | boolean | 业务是否通过（配套且可登录） |
| `code` | string | 业务码，见 §2.4 |
| `message` | string | 给人看的说明；提案可透传或映射文案 |
| `data` | object \| null | 仅 `code=0` 时有值 |

### 2.4 业务码

| code | success | 含义 | 提案前端提示（建议） |
|------|---------|------|----------------------|
| `0` | true | 工号存在、手机配套、在职可登录 | — |
| `1001` | false | 工号不存在 | 工号或手机号不正确，请修改后重试 |
| `1002` | false | 工号存在但与登记手机不配套 | 工号与手机号不匹配，请修改后重试 |
| `1003` | false | 员工不在职 / 无系统权限 | 账号不可用或已离职，请联系管理员 |
| `1099` | false | 其它业务拒绝 | 使用 `message` 或统一「校验失败」 |

> HTTP 层：正常业务拒绝仍建议 **HTTP 200 + 上述 code**；仅网络/鉴权/服务异常用 4xx/5xx。

## 3. 成功时 `data` 字段清单（HR 需返回）

以下为 **提案侧决定的最小+推荐集**，供 HR 按口径出数。  
标注「落库」的字段会在用户 **短信登录成功** 后写入本地；标注「缓存」的在发码阶段进 Redis，登录成功再落库。

### 3.1 身份与状态（必填）

| 字段 | 类型 | 必填 | 本地落点 | 说明 |
|------|------|------|----------|------|
| `workNo` | string | 是 | `sys_user.username` = `sys_user.work_no` | 须与请求 `workNo` 一致 |
| `realname` | string | 是 | `sys_user.realname` | 姓名 |
| `mobile` | string | 是 | `sys_user.phone` | 登记手机；须与请求 `mobile` 一致（规范化后） |
| `employStatus` | string | 是 | 映射 `sys_user.status` | 枚举见下；非在职不得 `code=0` |

`employStatus` 枚举：

| 值 | 含义 | 提案处理 |
|----|------|----------|
| `ACTIVE` | 在职 | 允许发码/登录；`status=1` |
| `INACTIVE` | 离职/停用 | 须返回 `code=1003`，不要给 `data` |

### 3.2 组织归属（必填，用于挂本地部门树）

本地 **只保留组织架构、人员按登录灌入**。组织节点已在 `sys_depart`（中心→部门→组别）。  
HR 请返回名称路径，提案用「中心+部门+组别」匹配已有部门；**不要**把 HR 小组编码写入 Jeecg `org_code`。

| 字段 | 类型 | 必填 | 本地落点 | 说明 |
|------|------|------|----------|------|
| `centerName` | string | 是 | 匹配 `sys_depart`（CENTER） | 如「斯派科」「智能制造中心」 |
| `deptName` | string | 是 | 匹配 `sys_depart`（DEPT） | 如「自动线开发部」 |
| `groupName` | string | 是* | 匹配 `sys_depart`（GROUP） | 如「MES开发」；无组别时见规则 |

\* 若干部挂在部门级、无组别：`groupName` 可传 `""` 或 `null`，提案挂到 `deptName` 对应部门节点（与现网副经理挂载一致）。

匹配成功后写入：

- `sys_user.org_code` ← 匹配到的 `sys_depart.org_code`
- `sys_user_depart` ← `user_id` ↔ 该 `dep_id`（无则增、有则改到最新部门）

匹配失败（名称对不上本地树）：发码失败，提示「组织未同步，请联系管理员」（**不调短信**）。

### 3.3 岗位（必填）

| 字段 | 类型 | 必填 | 本地落点 | 说明 |
|------|------|------|----------|------|
| `positionName` | string | 是 | `sys_user.position_type` | 岗位名称原文，如「高级主管」「JAVA开发工程师」 |

> 不强制 HR 对齐 Jeecg 职务字典 ID；先存文本，展示用。

### 3.4 三级审批者（必填，档案用）

与流程图一致：登录成功后写入员工档案快照；**不自动覆盖**提案委员会 / 部门负责人 / 批准人配置表。

| 字段 | 类型 | 必填 | 本地落点（建议） | 说明 |
|------|------|------|------------------|------|
| `approverL1WorkNo` | string | 是 | 扩展/旁路表，见 §5 | 一级审批者工号 |
| `approverL1Name` | string | 是 | 同上 | 一级审批者姓名 |
| `approverL2WorkNo` | string | 是 | 同上 | 二级审批者工号 |
| `approverL2Name` | string | 是 | 同上 | 二级审批者姓名 |
| `approverL3WorkNo` | string | 是 | 同上 | 三级审批者工号 |
| `approverL3Name` | string | 是 | 同上 | 三级审批者姓名 |

若某级空缺：工号、姓名传 `""`，不要省略字段。

### 3.5 推荐选填（有则更好）

| 字段 | 类型 | 必填 | 本地落点 | 说明 |
|------|------|------|----------|------|
| `hrGroupCode` | string | 否 | 仅日志/对账，**不写** `org_code` | 如 Excel「所属小组编码」`05010303` |
| `jobLevelCode` | string | 否 | 暂不落库或进扩展 | 职级代码，如 `M9` |
| `jobLevelName` | string | 否 | 暂不落库或进扩展 | 职级名称 |
| `hireDate` | string | 否 | 暂不落库或进扩展 | `yyyy-MM-dd` |

> **本期不要求**：`email`（邮箱）。HR 可不返回；提案侧登录同步也不依赖邮箱。

## 5. 提案侧落库边界（给 HR 对齐预期，非 HR 实现项）

| 类别 | 行为 |
|------|------|
| 用户主数据 | 按 `workNo`：**无则创建，有则更新** §3.1～3.3（不含邮箱） |
| 部门挂载 | 按名称路径匹配本地 `sys_depart`，更新 `org_code` + `sys_user_depart` |
| 三级审批者 | 登录成功写入档案快照（表结构实现阶段定）；**不写** `proposal_committee_member` / `proposal_dept_leader` / `proposal_approver` |
| 绝不覆盖 | `password` / `salt`、角色授权、提案配置名册、微信绑定以外的业务单据 |
| 微信绑定 | `sys_third_account`：`user_id` ↔ `openid`；与 HR 接口无关，由提案后端用微信 `code` 自换 |

新建用户时（无本地账号）：

- `username` = `workNo`
- 可生成随机不可用密码或占位（正式登录走短信；测试阶段仍可用管理端重置后走密码登录）
- `status=1`，`del_flag=0`

## 7. 与短信登录流程图的关系

本接口对应流程图中 **「调 HR 校验工号+手机」** 节点：

1. 提案后端收齐：工号 + 手机 + 微信 `code`（发码接口）  
2. 调本 HR 接口 → 失败则结束  
3. 后端换 `openid`、做占用检查 → 发短信，并把本 `data` 快照写入 Redis（如 `hr:{workNo}:{mobile}`，TTL≈300s）  
4. 登录成功后再按 §5 落库  

**前端不传 HR 员工包，不传 openid。**
