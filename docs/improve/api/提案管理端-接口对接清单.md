## 1. 联调约定（先看这段）

| 项 | 说明 |
|----|------|
| Base URL | `http://{host}:8080/jeecg-boot`；Vue3 开发环境走代理，`defHttp` 路径写相对路径即可 |
| 鉴权 | 请求头 `X-Access-Token: <JWT>`（Jeecg 管理端登录后自动带） |
| 登录 | `POST /sys/login`，`username` = **工号**（`workNo`）；密码走平台既有 AES，**不要自己再包一层** |
| Content-Type | JSON 接口：`application/json` |
| 统一响应 | Jeecg `Result`：`{ success, code, message, result }`；业务成功常见 `code` 为 `200` 或 `0` |
| 业务报错 | `success=false`，`message` 为中文提示，前端直接 `createMessage` 即可 |
| Knife4j | `http://localhost:8080/jeecg-boot/doc.html` → 标签「管理端-提案管理」「管理端-提案配置」「提案元数据」 |
| 菜单 SQL | `docs/improve/sql/proposal_menu.sql`；执行后需在「角色管理」给 `admin` / `proposal_admin` 授权 |

### 1.1 路径前缀约定

| 前缀 | 用途 | 本清单 |
|------|------|--------|
| `/proposal/admin/manage/**` | 提案管理（后台列表/详情） | ✅ 重点 |
| `/proposal/admin/config/**` | 提案配置（五 Tab CRUD） | ✅ 重点 |
| `/proposal/meta/**` | 公共元数据（`ProposalMetaController`） | ✅ 筛选下拉全量，见 §4 |
| `/sys/**` | 登录、用户/部门回显、选人选部门 | ✅ 必要（名称不在业务接口里） |
| `/proposal/**`（`ProposalController`） | 共用生命周期：发起/撤回/委员审/批准 | ⚪ 已盘点；**管理端不对接**，见 §2.1 |
| `/proposal/app/**` | 小程序首页聚合 | ❌ 不对接 |
| `/proposal/admin/stats/**` | 管理端统计 | ❌ 尚未交付 |

### 1.2 页面范围（当前产品）

| 菜单 | 路由 | 组件 | 当前能力 |
|------|------|------|----------|
| 提案改善（目录） | `/proposal` | `layouts/RouteView` | — |
| 提案管理 | `/proposal/manage` | `mes/proposal/manage/index` | **仅查询 + 详情**，无新增/编辑/删除/勾选 |
| 提案配置 | `/proposal/config` | `mes/proposal/config/index` | 五 Tab 全量 CRUD |

> 后端虽保留 `POST /add`、`PUT /edit`、`DELETE /delete`，**当前管理端页面不要接**。提案的发起/审核/批准走小程序。

### 1.3 配置五 Tab

| Tab | 配置表 | 业务作用 |
|-----|--------|----------|
| 部门负责人 | `proposal_dept_leader` | 提交申请前校验；一部门一人 |
| 委员会 | `proposal_committee_member` | 审核名册；`scoreEnabled` 控制是否参与后期评分 |
| 批准人 | `proposal_approver` | 申请/计划书/报告书终审；列表接口只返回 `active` |
| 改善性质 | `proposal_improvement_type` | 发起页芯片 + 列表筛选；**不要写死码** |
| 评分维度 | `proposal_score_dimension` | 后期六维评分权重；本阶段只做配置维护 |

### 1.4 通用字段（所有 `proposal_*` 表）

保存时后端会补审计字段，前端**不必传** `createBy` / `updateBy`。列表展示可用 `updateBy`、`updateTime`。

| 字段 | 说明 |
|------|------|
| `id` | 主键；新增不传，编辑必传 |
| `createBy` / `createTime` | 创建人名称 / 时间 |
| `updateBy` / `updateTime` | 更新人名称 / 时间 |
| `remark` | 备注，可选 |
| `active` | 逻辑删除：`Y` 有效 / `N` 已删；列表默认只出有效行 |

### 2.1 公共 Controller 全量对照

包路径：`org.jeecg.modules.proposal.controller`（与 `admin/`、`app/` 平级）。  
**结论**：10 个生命周期接口管理端都不要调；3 个元数据接口管理端要用（B1 可选，B2/B3 必用）。

#### `ProposalController`（`/proposal`）— 小程序主链路

| 方法 | 路径 | 做什么 | 管理端 |
|------|------|--------|--------|
| POST | `/proposal/create` | 创建草稿 | ❌ 只给提案人；后台无「新增提案」 |

| PUT | `/proposal/{id}/submit` | 提交申请 | ❌ |
| POST | `/proposal/{id}/withdraw` | 撤回 | ❌ |
| GET | `/proposal/list` | **当前登录人**的「我的提案」 | ❌ 不是全量；全量用 M1 |
| GET | `/proposal/{id}` | 详情（按角色鉴权） | ❌ 委员/批准人看不见别人的单；全量详情用 M2 |

## 3. 提案管理

### M1 分页列表

```http
GET /proposal/admin/manage/list
```

走 Jeecg `QueryGenerator`：查询参数名与实体字段一致。分页：`pageNo`（默认 1）、`pageSize`（默认 10）。默认 `create_time` 倒序。

| 参数 | 对应筛选项 | 说明 |
|------|------------|------|
| `proposalNo` | 提案编号 | 精确；需要模糊可传 `*202608*` |
| `title` | 提案名称 | 同上 |
| `status` | 当前环节 | 状态码，来自 B2，如 `PENDING_REVIEW` |
| `deptId` | 改善部门 | `sys_depart.id`；`JSelectDept` 若返回数组/逗号串，**只取第一个** |
| `improvementTypes` | 改善性质 | 落库是 JSON 字符串。单选筛选请传 `*SAFETY*`（前后星号 = LIKE） |
| `proposerName` | 提案人 | **不是实体字段**；后端按 `sys_user.realname` 模糊搜 `proposer_id` |
| `createTime_begin` / `createTime_end` | 提交日期 | 日期范围，格式 `YYYY-MM-DD`；Vue3 可用 `fieldMapToTime` |

**`result`：** MyBatis-Plus 分页：

```json
{
  "records": [
    {
      "id": "...",
      "proposalNo": "202608290001",
      "title": "...",
      "status": "PENDING_APPROVAL",
      "statusLabel": "待批准",
      "improvementTypes": "[\"SAFETY\",\"EFFICIENCY\"]",
      "improvementTypesLabel": "安全改善 / 效率改善",
      "deptId": "spexdeptgroupelc0000000000001",
      "proposerId": "...",
      "deptLeaderId": "...",
      "planRequired": 1,
      "awardAmount": 150,
      "reviewProgress": "5/5",
      "createTime": "2026-08-29 14:00:00"
    }
  ],
  "total": 1,
  "current": 1,
  "size": 10
}
```

| 字段 | 是否后端直接给 | 说明 |
|------|----------------|------|
| `statusLabel` | ✅ | 中文环节，列表 Tag 优先用这个，不要自己映射字典 |
| `improvementTypesLabel` | ✅ | 中文性质，用 ` / ` 拼接 |
| `proposerName` | ❌ | 需 S1 用 `proposerId` 换 `realname` |
| `deptName` | ❌ | 需 S2 用 `deptId` 换 `departName` |
| `reviewProgress` | ✅ | 字符串 `"3/5"`，可拆成进度条 |
| `awardAmount` | ✅ | 未核定为 `null`，展示 `-` |

列表列建议（对齐原型）：提案编号 | 提案名称 | 提案人 | 改善部门 | 改善性质 | 当前环节 | 审核进度 | 核定提案奖 | 提交时间 | 详情。

### M2 详情（管理端）

```http
GET /proposal/admin/manage/queryById?id=<提案id>

管理端专用：比小程序详情多 `statusLogs`。无提案人/委员权限限制，有菜单即可看。

  "application": { "currentSituation", "improvementSuggestion", "submitTime" },
  "attachments": [ { "fileName", "fileUrl", "fileSize", "sortNo", "bizType" } ],
  "committeeReviews": [
    {
      "id": "...",
      "reviewerId": "...",
      "conclusion": "ADOPT",
      "planRequired": 1,
      "awardSuggestion": 150,
      "comment": null,
      "reviewTime": "2026-08-29 15:00:00"
    }
  ],
  "applicationApproval": {
    "approverId": "...",
    "stage": "APPLICATION",
    "decision": "APPROVE",
    "planRequired": 1,
    "awardAmount": 150,
    "comment": null,
    "approveTime": "2026-08-29 16:00:00"
  },
  "statusLogs": [
    {
      "action": "SUBMIT",
      "actionLabel": "提交申请",
      "fromStatus": "DRAFT",
      "fromStatusLabel": "草稿",
      "toStatus": "PENDING_REVIEW",
      "toStatusLabel": "待审核",
      "operatorId": "...",
      "createTime": "2026-08-29 14:10:00"
    }
  ]

```

| 块 | 说明 |
|----|------|
| `application` | 申请书正文；草稿可能几乎为空 |
| `attachments` | 现场图，最多 4 张；`fileUrl` 拼静态资源前缀展示 |
| `committeeReviews` | **含未审行**：`conclusion` / `reviewTime` 为空 |
| `applicationApproval` | 未决策时为 `null` |
| `statusLogs` | 操作留痕，按时间倒序；`actionLabel` / 状态 Label 后端已填 |

详情弹窗建议结构（对齐原型）：

1. 摘要卡：编号、名称、状态 Tag、审核进度、核定奖、是否形成计划书  
2. Tab「申请单」：目前状况 / 改善意见 / 附件  
3. Tab「委员意见」：姓名、已审/待审、采用/不采用、计划书建议、奖励建议、说明  
4. Tab「计划书 / 报告书」：本阶段占位即可  
5. Tab「操作留痕」：时间、动作、从→到、操作人  

文案映射（后端已给 Label 时优先用接口字段）：

| 码 | 中文 |
|----|------|
| `conclusion=ADOPT` / `REJECT` | 采用 / 不采用 |
| `decision=APPROVE` / `REJECT` | 批准 / 不批准 |
| `planRequired=1` / `0` | 形成 / 不形成 |
| `action=SUBMIT` | 提交申请 |
| `action=WITHDRAW` | 撤回申请 |
| `action=COMMITTEE_DONE` | 委员审核完成 |
| `action=APPROVE` | 申请批准 |
| `action=REJECT_FINAL` | 申请不批准 |

**提案人「部门」≠「改善部门」：**

| 展示 | 数据来源 |
|------|----------|
| 改善部门 | `proposal.deptId` → S2 `departName` |
| 提案人所属部门 | `proposerId` → S1 得 `orgCode` → S3 `departName` |
| 部门负责人 | `proposal.deptLeaderId` → S1 `realname` |

## 4. 元数据（筛选下拉，来自公共 `ProposalMetaController`）

三个接口都在 `/proposal/meta/**`，登录即可调，和小程序同一套。

### B1 改善部门下拉（可选）

```http
GET /proposal/meta/improvementDepts
```

来自 `proposal_dept_leader`（`active=Y`），**已带部门名和负责人名**，不必再调 S2。只返回「配过改善部门」的行，比 `JSelectDept` 全组织树更贴筛选语义。

**`result` 数组元素：**

| 字段 | 类型 | 说明 |
|------|------|------|
| `deptId` | string | 改善部门 ID（筛 `deptId` 用这个） |
| `deptName` | string | 部门名称 |
| `leaderUserId` | string | 负责人用户 ID，可空 |
| `leaderName` | string | 负责人姓名，未配置时为 `null` |
| `leaderConfigured` | boolean | 是否已配负责人 |

当前仓库列表筛选用的是 `JSelectDept`（全部门树）。若改成只筛「已配置改善部门」，直接接本接口即可。配置页「新增部门负责人」仍用 `JSelectDept`，因为要选尚未配置的部门。

### B2 提案状态

```http
GET /proposal/meta/statuses
```

来自后端枚举，**不是数据字典**。`result` 数组：`{ code, label, terminal }`。

申请段常见：`DRAFT` 草稿、`PENDING_REVIEW` 待审核、`PENDING_APPROVAL` 待批准、`REJECTED_FINAL` 不批准、`WITHDRAWN` 已撤回、`PENDING_ASSIGN` 待指派。后续状态也会返回，筛选下拉可全量展示。

### B3 改善性质

```http
GET /proposal/meta/improvementTypes?enabledOnly=true
```

来自配置表。默认只返回启用项（列表筛选、发起芯片）。`enabledOnly=false` 含停用，用于旧单回显。

`result` 数组：`{ code, label, typeStatus, sortNo, description }`。

种子码（可在配置里改名/停用/新增，**前端不要写死文案**）：

| code | 种子名称 |
|------|----------|
| `SAFETY` | 安全改善 |
| `QUALITY` | 品质改善 |
| `EFFICIENCY` | 效率改善 |
| `DELIVERY` | 交付改善 |
| `COST` | 成本改善 |

## 5. 系统接口（名称回显 / 选人）

业务接口只存 `sys_user.id` / `sys_depart.id`，姓名、工号、职位、部门名要自己换。`JSelectUser` / `JSelectDept` 组件内部请求可沿用 Jeecg 默认，不必改。

### S1 用户批量查询

```http
GET /sys/user/queryByIds?userIds=id1,id2,id3
```

`result` 为用户数组，常用字段：`id`、`realname`、`workNo`、`username`、`positionType`（职位，不是 `post`）、`orgCode`。

### S2 部门批量查询

```http
GET /sys/sysDepart/queryByIds?deptIds=id1,id2
```

`result` 为部门数组：`id`、`departName`。优先用 `departName`；`departPathName` 在 `org_code` 不规则时可能报错或为空。

### S3 按组织编码取部门

```http
GET /sys/sysDepart/getDepartName?orgCode=A01A02
```

`result` 为单个部门，取 `departName`。用于提案人**所属部门**回显。

### S4 按部门选用户（部门负责人弹窗）

```http
GET /sys/user/queryUserComponentData?departId=<deptId>&pageNo=1&pageSize=10
```

只列出该部门（及下级）人员。未选改善部门时不要调，前端给空列表即可。

选人/选部门组件注意：Jeecg 有时返回 **数组或逗号串**，提交配置前务必收成**单个 id**。

## 6. 提案配置

除特别说明外：保存均为 `POST` + JSON Body；删除均为 `DELETE ?id=`（Vue3 可用 `joinParamsToUrl: true`）。无 `id` = 新增，有 `id` = 更新。

### 6.1 部门负责人（C1–C3）

**列表** `GET /proposal/admin/config/deptLeader/list` → **分页** `{ records, total }`。

**保存 Body：**

```json
{
  "id": "编辑时传",
  "deptId": "sys_depart.id",
  "leaderUserId": "sys_user.id",
  "remark": "可选"
}
```

| 规则 | 说明 |
|------|------|
| 一部门一行 | 唯一键 `(dept_id, tenant_id)`，重复部门会失败 |
| 编辑时部门不可改 | 前端 `deptId` 禁用 |
| 先选部门再选人 | 人选范围用 S4，限定本部门 |
| 未配负责人 | `leaderUserId` 可空；列表显示「未配置」；小程序提交该部门会被拒 |

列表需前端补：`deptName`、`leaderRealname`、`leaderWorkNo`、`leaderPosition`（`positionType`）。

### 6.2 委员会（C4–C6）

**列表** `GET /proposal/admin/config/committee/list` → **分页**。排序：`sort_no`、`seat_no`。

**保存 Body：**

```json
{
  "id": "编辑时传",
  "userId": "sys_user.id",
  "scoreEnabled": 1,
  "seatNo": 1,
  "memberStatus": "active",
  "sortNo": 0,
  "remark": "可选"
}
```

| 字段 | 说明 |
|------|------|
| `userId` | 一人一行，唯一键 `(user_id, tenant_id)` |
| `scoreEnabled` | `1` 参与后期六维评分；`0` 只审核不评分 |
| `seatNo` | `scoreEnabled=1` 时必填（1–99）；`=0` 时后端会把 `seatNo` 置空 |
| `memberStatus` | `active` 在任 / `inactive` 离任；审核只认在任 |

列表需前端补姓名/工号/所属部门/职位。评分职责展示：`scoreEnabled===1 && seatNo` → `评分席位 N`，否则 `不参与评分`。

### 6.3 批准人（C7–C9）

**列表** `GET /proposal/admin/config/approver/list` → **数组 `List`，不是分页**。只返回 `approver_status=active`。前端可包成 `{ records, total }` 给表格。

业务上通常全局一人；原型做成卡片（姓名/工号/部门/职位 + 更换/移除）。签核范围文案可写死展示：「申请单终审 / 计划书终审 / 报告书终审」（后端暂无该字段）。

**保存 Body：**

```json
{
  "id": "编辑时传",
  "userId": "sys_user.id",
  "approverStatus": "active",
  "remark": "可选"
}
```

未传 `approverStatus` 时后端默认 `active`。

### 6.4 改善性质（C10–C12）

**列表** `GET /proposal/admin/config/improvementType/list` → **数组 `List`**（含停用）。排序：`sort_no`、`type_code`。

**保存 Body：**

```json
{
  "id": "编辑时传",
  "typeCode": "SAFETY",
  "typeName": "安全改善",
  "description": "可选说明",
  "sortNo": 1,
  "typeStatus": "active"
}
```

| 规则 | 说明 |
|------|------|
| `typeCode` | 新增必填；字母开头，仅字母数字下划线，最长 32 |
| 编码创建后不可改 | 编辑时后端强制沿用原 `typeCode`，前端应禁用编码框 |
| 编码唯一 | 重复提示「性质编码已存在」 |
| `typeStatus` | `active` / `disabled`；未传默认 `active` |
| 删除 | 已有提案引用该码会失败，提示改为**停用**；未被引用才物理删除（可重用编码） |

停用后：新提案不能再选；旧单靠 `improvementTypesLabel` 回显。

### 6.5 评分维度（C13–C15）

**列表** `GET /proposal/admin/config/scoreDimension/list` → **数组 `List`**。排序：`sort_no`。

种子六维（可改名称/权重/启停，编码一般不要改）：

| dimCode | 种子名称 | 种子权重 |
|---------|----------|----------|
| `tangible` | 有形绩效 | 30 |
| `intangible` | 无形绩效 | 10 |
| `difficulty` | 难易度 | 20 |
| `spread` | 推广性 | 15 |
| `completeness` | 完成度 | 10 |
| `innovation` | 创新性 | 15 |

**保存 Body：**

```json
{
  "id": "编辑时传",
  "dimCode": "tangible",
  "dimName": "有形绩效",
  "description": "可选",
  "weightPct": 30,
  "sortNo": 1,
  "dimStatus": "active"
}
```

`dimStatus`：`active` / `disabled`。前端可对启用项的 `weightPct` 求和，原型要求合计 100%（后端暂不强制校验）。

## 9. 前端注意点（踩坑清单）

1. **业务接口不返回姓名/部门名**：必须 S1/S2/S3 二次查询；不要把 `proposerId` 直接展示给用户。
2. **提案人部门 ≠ 改善部门**：前者是申请人 `orgCode` 对应部门，后者是 `proposal.deptId`。
3. **`improvementTypes` 是 JSON 字符串**：列表筛选传 `*SAFETY*`；展示优先用行内 `improvementTypesLabel`。
4. **状态/性质不要走 Jeecg 字典**：用 B2/B3；Tag 颜色可前端写，文案用接口 Label。改善部门筛选优先考虑 B1（已配置部门），不要和配置页的全量 `JSelectDept` 混用。
5. **批准人 / 改善性质 / 评分维度列表是 `List`**：不是 `{ records, total }`，取数时判断 `Array.isArray`。
6. **选人组件可能返回数组**：保存前收成单个 id（`deptId`、`leaderUserId`、`userId`）。
7. **职位字段是 `positionType`**，不是 `post`。
8. **S2 若因 `org_code` 报「编码长度必须能被固定位数整除」**：catch 后降级显示 id，不要让整页挂掉。
9. **提案管理不要接 add/edit/delete**：即使后端有接口。
10. **改善性质已引用不可删**：引导改停用；编码创建后不可改。
11. **委员 `scoreEnabled=0` 时不要传席位号**；后端会清空 `seatNo`。
12. **删除接口把 `id` 放 Query**：`DELETE .../delete?id=`。
